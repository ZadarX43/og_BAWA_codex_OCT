# Website Remaining Workstack

## Purpose

This document is the current source of truth for what still needs to be built on the Odds Genius website and delivery stack.

It exists to separate:

- what is already live
- what is partially built
- what is the real next work
- what is intentionally deferred

This is a website and product workstack document.
It does not change the protected football prediction spine.

## Current Product Position

Odds Genius is no longer only:

- a predictions page
- a premium gate
- a Telegram side-channel

It is now operating as:

- a published football intelligence surface
- a personalised follow and delivery layer
- a premium account product
- a selective Telegram intelligence system

The website now already has:

- homepage
- predictions
- results
- premium board
- methodology
- pricing
- account
- dashboard
- fixture intelligence pages
- saved follows and preferences
- Telegram linking
- Telegram test sends
- followed-intelligence matching
- queued Telegram alert infrastructure
- cron-ready selective delivery

That means the remaining work is no longer “make the website exist.”

The remaining work is:

- make the website calmer
- make the intelligence deeper
- make the delivery sharper
- make the proof layer stronger
- make the account/commercial layer more complete
- make the platform more reliable

## Current Strategic Principle

The master product principle is:

> Clarity replacing chaos.

This means:

- website can stay broad and intelligence-rich
- Telegram should stay selective and interruption-worthy
- `PASS / NO EDGE` must feel intelligent, not empty
- losses and failed deploys should be absorbed with composure, not urgency

## Workstack Order

## Phase A — Calm Product UX

This is the next active website phase.

Build:

- dedicated onboarding flow
- user style presets
- fuller decision companion prompts
- reset / clarity mode for losses or failed deploys
- sharper alert scoring
- clearer dashboard buckets
- clearer explanation of:
  - why something interrupted via Telegram
  - why something stayed website-only

This phase should make Odds Genius feel more like:

- a disciplined analyst desk

and less like:

- a raw alert surface

### Immediate tasks inside Phase A

1. Task 71 — Calm Onboarding + Style Presets Plan
2. My Feed / My Alerts scoring refinement
3. Telegram vs website-only explanation layer
4. loss-state / failed-deploy reset copy and UX

## Phase B — Intelligence Depth

After calm product UX, the next layer is intelligence depth.

Build:

- true `PASS / NO EDGE` product state
- richer `CONTEXT` cards
- richer `MONITOR` cards
- fresher injury context
- fresher lineup context
- fresher weather context
- richer team-stat summaries
- stronger summaries for non-routed fixtures

The important rule:

`PASS / NO EDGE` should become a first-class product state, not just a softer way of saying weak `OBSERVE`.

This phase should make the platform more useful during:

- weak-signal periods
- no-signal periods
- incomplete-routing periods

## Phase C — Proof And Results

The next trust layer after intelligence depth is proof and archive quality.

Build:

- automated grading pipeline
- `weekly_results.json`
- `results_archive.json`
- richer results filters:
  - market
  - tier
  - league
  - week/window
- chart-ready proof surfaces

This phase matters because Odds Genius should not only publish:

- what was live

It should also clearly preserve:

- what happened
- how it graded
- how performance rolled up over time

## Phase D — Account And Commercial Polish

The account/commercial layer is functioning, but not yet complete.

Build:

- subscription management UX
- customer billing self-service
- cleaner redirects after auth or verification
- cleaner session banners
- board freshness metadata
- account metadata polish

This phase should make the account system feel like:

- a premium product surface

not:

- a working but unfinished operational shell

## Phase E — Reliability And Infra Hardening

Once the core calm UX and proof layers are stronger, the next layer is reliability hardening.

Build:

- better Worker logging
- rate limiting / abuse protection
- publish freshness metadata
- post-publish live smoke checks
- stronger premium cache rotation / purge strategy

This phase is about making the delivery system:

- quieter operationally
- more observable
- more trustworthy under load
